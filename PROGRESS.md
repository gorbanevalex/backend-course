## Пройдено

### Event loop и libuv
- Run-to-completion: синхронный код нельзя прервать, loop ждёт пустой стек
- Процесс сервера общий для всех пользователей: блокировка у одного — тормоза у всех; память тоже общая
- «Долгий ≠ блокирующий»: ожидание I/O не блокирует, CPU-работа блокирует
- libuv: два механизма — поллер ОС (сеть, без потоков) и пул потоков (fs, dns.lookup, crypto, zlib; `UV_THREADPOOL_SIZE`, по умолчанию 4)
- Эксперимент с pbkdf2 и размером пула: выполнен и объяснён (группировка 4 + 2)
- Забитый пул тормозит несвязанные ручки (очередь FIFO)
- Запросы в БД идут через поллер ОС, пул потоков не занимают
- Фазы loop: timers → poll → check → close; микрозадачи (nextTick → промисы) после каждого колбэка
- Фаза определяется типом колбэка; `setTimeout(fn, 0)` = «на ближайшей фазе timers»
- Пример с readFile: порядок sync → nextTick → promise → immediate → timeout, объяснён
- I/O vs CPU; «асинхронный API ≠ I/O» (bcrypt — CPU-работа в пуле)
- Шпаргалка: [docs/event-loop-cheatsheet.html](docs/event-loop-cheatsheet.html)

### Что блокирует сервер на практике
- `*Sync`-функции в обработчике; при старте сервера — нормально (выполняется один раз, клиентов ещё нет)
- Данные, размер которых задаёт клиент (`JSON.parse` большого тела) → лимит размера тела (`bodyLimit` в Fastify — 1 МБ по умолчанию)
- Тяжёлая обработка в JS вместо БД
- ReDoS: эксперимент выполнен, рост экспоненциальный (+1 символ = ×2 времени)
- Последствия в проде: растёт задержка всех ручек, падают health check'и, метрика event loop lag

### Модели серверов и ресурсы
- «Поток на запрос» vs Node: 10 000 ожидающих соединений ≈ 10 ГБ стеков потоков vs десятки МБ; ограниченный пул воркеров → очередь и рост задержки
- Go-горутины и виртуальные потоки Java 21+ — дешёвые потоки, похожая идея
- Ручка с 200 000 строк: риск 1 — CPU в JS-потоке, риск 2 — память процесса (GC-паузы, OOM для всех); решение — агрегация в БД, для больших объёмов — streams
